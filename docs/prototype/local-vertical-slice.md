# GP: локальный прототип «участок → зоны → материалы → BOM»

Дата решения: **2026-11-13**. Основание: владелец ответил «продолжи» на предложение разрешить **один ограниченный локальный Prototype Gate** в текущем диалоге. Это разрешение на ограниченный прототип, не на Market GO, релиз, SEO-контент или публикацию.

**Статусы:** GP = `AUTHORIZED_LOCAL_ONLY`; G1 Market Feasibility = `BLOCKED`; G8 Production = `NOT_AUTHORIZED`; G9 Post-launch = `N/A`.

## User job и единственный vertical slice

Владелец участка вводит размеры участка, создаёт несколько прямоугольных зон, указывает для каждой зоны материалы/слои и получает объяснимую сводную ведомость объёмов и (при достаточном вводе) масс и упаковок.

Разрешены только:
- площадь прямоугольного участка и перевод м² ↔ сотки ↔ гектары;
- несколько именованных прямоугольных зон по длине и ширине; визуально понятный список зон, **без** карты, геоданных, перетаскивания и автоматической проверки пересечений;
- для каждой зоны — слои материалов из фиксированного списка `грунт / щебень / песок`, с **вводимой пользователем** толщиной и запасом;
- группировка по материалу в одну ведомость (BOM); масса — только при введённой плотности, количество мешков — только при введённом объёме упаковки;
- локальный UI, мобильный и десктопный адаптив, доступность клавиатурой.

**Не входят:** забор, теплица, полив, агрономические рекомендации, подбор нормативов, прайс/смета, AI, учетные записи, внешние API, БД, геолокация, импорт/экспорт персональных данных, массовые SEO-URL, аналитика, РСЯ, DNS, публикация, деплой, сбор персональных данных.

## Математическая спецификация

Обозначения: `L, W` — метры; `h` — сантиметры; `r` — введённый запас, проценты; `ρ` — введённая плотность, кг/м³; `b` — введённая ёмкость мешка, литры.

1. Площадь прямоугольника: `A = L × W` (м²). `сотки = A / 100`; `гектары = A / 10 000`.
2. Базовый объём слоя: `V = A × h / 100` (м³); `литры = 1000 × V`.
3. Закупочный объём с резервом: `V_buy = V × (1 + r / 100)`. Базовый и закупочный объём показывать **раздельно**, никогда не прибавлять запас дважды.
4. При указанной `ρ`: `mass_kg = V_buy × ρ`; `mass_t = mass_kg / 1000`. Если плотность отсутствует — вывод `масса: не рассчитана`, а не ноль.
5. При указанном `b`: `bags = ceil(V_buy × 1000 / b)` — строго целое число закупаемых упаковок. Если `b` не указано — не выводить число мешков.
6. Ведомость: суммировать точные, ещё не округлённые `V` и `V_buy` по каждому материалу; считать мешки **после суммирования**, если размер упаковки для этого материала единый. При неодинаковых плотностях или размерах упаковки не выдавать заведомо ложную суммарную массу/мешки; показывать раздельно по вариантам или явный `не определено`.
7. Границы: положительные конечные L, W, h, b, ρ; `r ≥ 0` с оговорённой верхней границей; переполнение и неопределённые значения — ошибка ввода. Не делать расчёты из визуально округлённых промежуточных величин.
8. Никакие нормы глубины, плотности, потерь/запаса, упаковки и цены **не задавать от имени эксперта**. Демонстрационные значения — явно помеченные редактируемые примеры, не рекомендации.

## Независимые golden cases

- Прямоугольник 20 × 30 м → 600 м² → 6 соток → 0,06 га.
- Грунт: зона 4 × 6 м, слой 25 см → 24 м², 6 м³ = 6000 л. Запас 10% → 6,6 м³; мешок 50 л → 132 мешка.
- Щебень: зона 2 × 10 м, слой 8 см → 1,6 м³; запас 5% → 1,68 м³. При **введённой** плотности 1500 кг/м³ → 2520 кг = 2,52 т.
- Песок: та же площадь 20 м², слой 4 см → 0,8 м³; запас 5% → 0,84 м³. При **введённой** плотности 1600 кг/м³ → 1344 кг = 1,344 т.
- Граница упаковок: ровно 100 литров при размере мешка 50 л → 2; любое корректное представимое значение строго больше 100 литров → 3. Не допускать ошибочного `ceil` из-за бинарных float-артефактов.
- Суммирование: два слоя грунта по 25 л, общий размер мешка 50 л → **1**, не 2 отдельных мешка. Отсутствующая плотность одной из зон не должна приводить к фиктивной общей массе.
- Проверить запятые в русских числах, промежуточные `-`, `,`, `1,`, пустые/отрицательные/NaN/Infinity/слишком большие значения.

## UX и доказательства

- Первая рабочая область — сам калькулятор, а не маркетинговый hero.
- Поля контролируемые; при временно некорректном вводе пользовательский текст не теряется; ошибки конкретны и привязаны к полям.
- Прозрачный результат: исходные данные → формула → вычисление → закупочный запас → BOM; предупреждение, что геометрические зоны не проверяются на перекрытие и не являются межеванием.
- На первом прототипе **нет гарантированного сохранения после reload**; если persistence не реализована, прямо сообщить это. Не обещать Share URL.
- Чистая предметная визуальная система, без утверждения пока не существующих токенов/шрифтов; макет/скриншоты согласуются отдельно до UI-кода.
- Реальный browser QA: 320 / 390 / 768 / 1024 / 1440 CSS px, клавиатура, touch simulation, ввод с запятой, редактирование/удаление зоны, ошибки, пересчёт BOM, back/reload. Физическое устройство = `BLOCKED_DEVICE`, если не проверялось.
- Для вычислений: независимые unit/golden/property тесты, включая монотонность, масштабирование, перевод единиц, границы округления и агрегирование.
- Точное происхождение параметров, формул и отсутствие придуманных нормативов обязательно.

## Технические и релизные границы

Предварительный вариант — Next.js + TypeScript, статическая локальная страница и pure calculation module без backend. **Не окончательное архитектурное решение**: перед реализацией следует проверить версии и зависимости, зафиксировать их в отдельном implementation PR.

Первый PR с кодом ограничивается одним вертикальным срезом, без генерации каталога URL. Реальный `npm test/build` и browser QA обязательны; docs-only CI не доказательство готовности приложения. Результаты фиксировать как `PASS / BLOCKED / FAIL / NOT RUN`, указывая точный коммит.

Запрещены публикация, деплой, смена DNS, индексация, аналитика, реклама, автоматический merge. Отдельные owner approvals обязательны для расширения scope и продакшена.
