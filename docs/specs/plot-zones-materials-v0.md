# Дачаметр — первый вертикальный срез: участок → зоны → материалы → BOM

**Версия спецификации:** `draft-v0.3`, 13.11.2026. **Статус:** PROPOSED, NOT APPROVED. Документ описывает техническую модель и будущую приёмку, **не разрешает создание Next.js-приложения**, публичный deploy или изменение Gate 1 (BLOCKED). Первоначальное исследование: `docs/research/mvp-prioritization.md` и `docs/research/gate-1-decision.md`.

## 1. Пользовательская задача и границы
Пользователь планирует прямоугольный участок, вводит несколько прямоугольных зон (грядки и основания дорожек), указывает слои грунта/песка/щебня, толщину, собственный запас и, при необходимости, упаковку или насыпную плотность. Получает **проверяемый объём по каждой зоне** и **общую ведомость закупки (BOM)**, не вводя одни и те же размеры повторно.

Исследование подтверждает наличие поисковых формулировок для расчётов грунта, площади участка и сыпучих материалов. **Потребность именно в объединённом сценарии пока гипотеза**: по этой спецификации нельзя объявить SEO market GO. Для локального прототипа потребуется отдельное решение владельца в `docs/decisions.md`.

**Входит в v0:** прямоугольный участок, зоны-прямоугольники, несколько слоёв на зону, типы `soil`/`sand`/`gravel`, расчёт м²→м³→л, индивидуальный запас, опциональная плотность кг/м³, опциональная упаковка в литрах, суммарный BOM по сопоставимым спецификациям. Все вычисления детерминированные, без сервера.

**Не входит:** геодезия, GPS/кадастр, сложные многоугольники и расстановка зон на карте, гарантированное отсутствие пересечений зон, подбор конструкции основания, масса без плотности, универсальные плотности и нормы слоёв, влажность/усадка/уплотнение, стоимость и локальные прайсы, инженерная устойчивость, транспортная грузоподъёмность, ввод «т» как пакет закупки, аккаунты, аналитика и сеть. Не добавлять их «заодно».

## 2. Модель данных (канонические единицы)
- `plot`: `length_m`, `width_m` — длина/ширина участка в метрах, строго положительные.
- `zones[]`: стабильный внутренний `id` (1–64 ASCII букв/цифр/`_`/`-`), название пользователя для UI, `length_m`, `width_m`; каждая зона содержит `layers[]`. Зоны могут оставаться без слоёв для планирования площади.
- `layers[]`: стабильный `id` (уникальный внутри зоны, 1–64 ASCII букв/цифр/`_`/`-`), `material` (`soil`, `sand`, `gravel`), `material_spec_id` (идентификатор конкретного пользовательского материала: 1–64 ASCII букв/цифр/`_`/`-`), `material_spec_label` (пользовательское название/марка/фракция: 1–80 символов Unicode после trim), `thickness_cm` (см), `reserve_percent` (%), `package_l` (литры **на упаковку**, опционально), `density_kg_m3` (кг/м³, опционально). Значения `density` не предзаполняются. Идентификаторы не зависят от индекса в массиве: удаление/перестановка не может переназначать введённые поля другому слою.
- Числовые поля хранятся как введённые **строки** в UI; доменная модель получает только конечные валидированные десятичные значения. Промежуточное `1,` не должно стираться, перескакивать или становиться `1` до окончания редактирования.
- В v0 технические диапазоны для валидации (НЕ агрономические нормы): `0 < length,width <= 100000 м`; `0 < thickness <= 1000 см`; `0 <= reserve <= 100%`; `0 < package_l <= 10^9 л`; `0 < density <= 100000 кг/м³`. Эти ограничители требуют подтверждения при утверждении прототипа и не должны подаваться пользователю как физически рекомендованные значения.
- В v0 также **предлагаются технические пределы нагрузки**, которые ещё требует утвердить владелец: до 50 зон, до 10 слоёв в каждой, до 80 Unicode-символов в пользовательском названии зоны. При превышении показывать точную ошибку до вычисления; не удалять элементы без подтверждения. Сложность вычисления должна быть ограничена числом слоёв; не допускать результат за безопасными пределами выбранной десятичной реализации. Эти лимиты не являются отраслевыми рекомендациями.
- При commit/submit допустимы строки `15`, `1.5`, `1,5`; пробелы по краям можно убрать. Не принимать неоднозначные `1,2.3`, `1 000`, `1e3`, `NaN`, `Infinity`; промежуточные `1,` и `-` хранятся без сообщения об ошибке до финальной валидации.
- В модели опциональные `package_l` и `density_kg_m3` задаются именно `null`, а не `0`, `""` или отсутствующим ключом; пустая строка в UI преобразуется в `null` только по явному правилу соответствующего необязательного поля. `null` в `package_l` означает покупку россыпью/по объёму; `null` в `density_kg_m3` означает **«масса неизвестна»**, а не ноль. Отсутствие числового значения и явный 0 никогда не отождествлять.

## 3. Формулы и порядок операций
Для зоны `z`, слоя `l`:
1. `A_z [м²] = L_z[м] × W_z[м]`.
2. `V_net(z,l) [м³] = A_z × thickness_cm / 100`.
3. `V_purchase(z,l) [м³] = V_net × (1 + reserve_percent / 100)`.
4. `purchase_l [л] = V_purchase [м³] × 1000`; `net_l = V_net × 1000`.
5. Если задана плотность: `mass_required_kg = V_purchase × density_kg_m3` — **масса требуемого объёма с запасом, но ДО округления упаковок**. Иначе масса `unknown`. Не называть её массой всех закупленных мешков.
6. BOM объединяет **только сопоставимые** позиции по ключу `(material_spec_id, material, package_l или bulk, density_kg_m3 или unknown)`. Уникальный `material_spec_id` обязателен у каждого слоя, назначается при создании нового варианта материала и повторно используется только по явному выбору пользователя. Одинаковые названия **не являются** разрешением на объединение. При повторном `material_spec_id` должны совпадать код вида (`soil`/`sand`/`gravel`) и метка после trim, иначе **ошибка всей модели** `conflicting_material_spec_definition`. Разные размеры упаковок или заданные плотности одного материала остаются отдельными строками BOM. Для каждого ключа: `BOM_purchase_l = Σ purchase_l`, `BOM_net_l = Σ net_l`. Если `package_l` задана, `packages = ceil(BOM_purchase_l / package_l)`; иначе число упаковок отсутствует. Значения по зонам остаются видимыми. Численно равные параметры, записанные как `1500` и `1500.0`, считаются одинаковыми; сравнение идёт по нормализованному числовому значению, не по строковому представлению.
7. **Сначала суммировать точные десятичные объёмы каждой позиции, затем округлить до закупочных упаковок.** Для упакованного материала: `packed_volume_l = packages × package_l`, `surplus_l = packed_volume_l − BOM_purchase_l`; для покупки россыпью оба поля равны `unknown`. Если введена плотность, `mass_purchased_kg = (packed_volume_l или BOM_purchase_l для bulk) / 1000 × density_kg_m3`; иначе `unknown`. Не суммировать округлённые упаковки зон, не выдавать объём с запасом за фактически покупаемый объём целых упаковок, не использовать округлённый UI-объём как вход следующего расчёта. Разная упаковка или плотность образует отдельную BOM-строку, даже если тип материала одинаков.
8. **Точность десятичных данных:** для расчёта `ceil` и сумм по объёмам нельзя полагаться на двоичные погрешности `Number`. В будущей TypeScript-реализации выбрать и зафиксировать проверяемую стратегию decimal/fixed-point/рациональных чисел (и границы безопасной точности) так, чтобы `0,1 + 0,1 + 0,1` при упаковке `0,3 л` давало **одну** упаковку. Произвольные `epsilon`-поправки без доказанного допуска запрещены. Упаковка может быть меньше 1 л. При выходе числа упаковок за поддерживаемый безопасный диапазон — явная ошибка, а не округление по ограничению JS Number.

9. Итог площади участка: `A_plot = plot.length_m × plot.width_m`; `ΣA_z` — сумма площадей зон. Если `ΣA_z > A_plot`, показать предупреждение, **не** автоматически вычитать зоны. При `ΣA_z <= A_plot` нельзя делать вывод, что зоны не пересекаются, поскольку их координаты не известны. «Свободная площадь» не рассчитывается и не обещается.

**Ограничение группировки:** пользователь вводит название конкретного материала, например «Грунт для грядок» или «Щебень 20–40 мм», но оно не подтверждает свойства и не задаёт нормативов. При создании каждого **нового** варианта генерируется новый `material_spec_id`; чтобы несколько зон использовали один материал, пользователь явно выбирает ранее созданный вариант. Совпадающее написание двух названий не означает тождество идентификаторов. Группировку определяет идентичность варианта и совместимость упаковки/плотности, а не тип материала и не совпадение названия. При одновременном изменении имени одного варианта отображение должно обновиться в каждой ссылающейся зоне без изменения её `material_spec_id`. Это схема для будущего UI, пока не реализованная.

Это **объём геометрического слоя по введённой толщине**, а не масса/трамбовка/потребность в закупке по строительной норме. Даже при введённой плотности масса — расчётная; качество материала, влажность и уплотнение могут менять фактическое количество.

### Ручные эталоны, независимые от будущего кода
| Проверка | Ручной расчёт | Ожидаемый итог |
| --- | --- | --- |
| Грядка 2×4 м; 25 см; 50 л | 2×4×0,25=2 м³=2000 л; 2000/50 | 40 мешков, без запаса |
| Две зоны 1×1 м; по 6 см; одна упаковка 50 л | 60+60=120 л; ceil(120/50)=3 | **3 мешка**, не 4 (по зонам) |
| Дорожка 2×5 м; песок 10 см+5%; щебень 5 см+10% | песок: 1000×1,05=1050 л; щебень: 500×1,1=550 л | Две BOM-позиции |
| Песок с введённой плотностью 1500 кг/м³ | 1,05 м³×1500 | 1575 кг (только с явной плотностью) |
| Щебень с введённой плотностью 1400 кг/м³ | 0,55 м³×1400 | 770 кг |
| 1×1 м; слой 5 см; упаковка 50 л | 50/50 | ровно 1 упаковка |
| 1×1 м; слой 4,9999 см; упаковка 50 л | 49,999/50 | **1 упаковка** |
| 1×1 м; слой 5,0001 см; упаковка 50 л | 50,001/50 | **2 упаковки** |
| Три зоны по 0,1 л; упаковка 0,3 л | (0,1+0,1+0,1)/0,3 | **1 упаковка** (без погрешности float) |
| Два слоя **одного выбранного варианта** грунта по 60 л, мешок 50 л | ceil((60+60)/50)=3; 3×50−120 | **3 мешка, 30 л сверх расчётного объёма** |
| Две разные марки грунта по 60 л, мешок 50 л | ceil(60/50) + ceil(60/50) | **4 мешка (по 2 каждого вида), без смешения марок** |
| 100 л грунта, мешок 60 л, плотность 1000 кг/м³ | 2 мешка=120 л; масса требуемых 100 кг, всех 2 мешков — 120 кг | **20 л сверх расчёта, масса закупки 120 кг** |

Все машиночитаемые примеры — `docs/specs/plot-zones-materials-cases.json`. В будущем TypeScript engine проверяется **по этим эталонам**, а не генерирует свои expected values.

## 4. Минимальный UX, без неутверждённой дизайн-системы
1. **Участок:** длина/ширина, площадь в м² и сотках (1 сотка = 100 м²), ясное пояснение «упрощённая прямоугольная геометрия».
2. **Зоны:** добавить/переименовать/удалить, ввести длину и ширину; результат площади рядом; не рисовать достоверный план размещения без координат.
3. **Слои зоны:** выбрать грунт/песок/щебень, затем **«Новый вариант материала»** (отдельный стабильный `material_spec_id`, пользовательское название без автоматически выдуманной марки) или **«Использовать имеющийся»** (явно выбрать уже созданный вариант); ввести толщину, запас, необязательную упаковку/плотность; видеть промежуточный объём и понятные формулы. Если две разные спецификации имеют одинаковый текст названия, UI явно разделяет их, не сливая расчёты.
4. **Ведомость:** отдельные строки по ключам материалов, чистый объём, объём с запасом, рассчитанная масса только при плотности, упаковки с округлением вверх, фактические литры всех упаковок и остаток `surplus_l`; если известна плотность — две разные массы (требуемая и фактическая упаковочная). Видна расшифровка по зонам.
5. **Состояния:** initial без зон, editing с `1,`, field-invalid после blur/submit, result, unknown density, package off, warning `ΣA_z > A_plot`, empty zones, add/delete zone, reset confirmation when data exist, reload/back, copy/print failure. Ошибка не стирает введённые значения. **При любой невалидной активной зоне или слое итоговая закупочная ведомость недействительна целиком**: нельзя молча исключить ошибочный слой и выдать оставшуюся сумму как готовую закупку. Показывать понятное сообщение `Исправьте ошибки, чтобы получить итоговую ведомость`; предыдущий результат скрыть или явно пометить устаревшим и не позволять копировать его как актуальный.
6. **Accessibility:** реальные `label`/`fieldset`, пояснение единиц, aria-live для итогов без спама, focus-visible, клавиатура, контраст и tap targets. Для модалок — управляемый фокус; не перехватывать pinch/scroll глобально.
7. **Responsive:** 320/390/768/1024/1440 CSS px, 200% zoom, длинные русские подписи, планшетный landscape + soft keyboard. Отдельный physical-device gate; desktop emulation не является evidence на Huawei/Yandex Browser.

**Модель состояния:** исходный ввод остаётся в клиентской памяти в ходе сессии; для v0 сохранение между перезагрузками и shareable URL **не обещаются**, пока не выбраны persistence strategy, schema version, privacy и тесты. После решения владельца можно отдельно одобрить URL state: только неконфиденциальные параметры, fail-closed и единый canonical для индексируемой страницы. Не закладывать скрытую telemetry.

## 5. SEO-связь
Предполагаемая будущая посадочная задача: расчёт материала по зонам участка, а не массовые страницы под размеры и синонимы. В v0 **нет одобренного индексируемого URL, Title, H1, FAQ или публичного домена**; `technical-seo` включается при отдельном release. Запрашиваемые параметры в будущем не должны создавать канонические дубликаты. Реальные Webmaster метрики/CTR/РСЯ неизвестны.

## 6. Приёмка и release gates
- G0 — этот договор и эталонные fixtures/QA, validators и CI на точном SHA.
- GP — **NOT AUTHORIZED** до отдельного решения владельца с указанием scope.
- G2 — формулы в настоящем доменном модуле, независимые fixture numbers, property tests, границы, десятичная точность, surplus/mass semantics, невалидный слой не даёт частичную ведомость; сейчас NOT RUN.
- G3 — реальный lint/typecheck/unit/integration/build и lockfile; сейчас NOT RUN.
- G4 — реальный браузер, error/result/reload, tablet/mobile, скриншоты/console/network; сейчас NOT RUN.
- G5/G8/G9 — SEO, production и post-launch только по отдельным решениям; сейчас NOT RUN / NOT AUTHORIZED.
- Не объявлять прототип `PASS` без фактического приложения и browser evidence. Не копировать Python/reference code в production JS как единственный источник истинности.

## 7. Нерешённые вопросы перед owner approval
1. Подтвердить **первую геометрию: прямоугольники** (без многоугольников и без координат зон).
2. Подтвердить, что плотность, слой, запас и размер упаковки **только пользовательский ввод**, никаких неаргументированных defaults (для запаса допускается нейтральный `0`).
3. Утвердить закупочную агрегацию: одинаковые тип материала/размер упаковки/плотность суммируются до `ceil`; для разных спецификаций — разные BOM-позиции.
4. Утвердить политику данных: локально без persistent/share URL в первом срезе; затем по отдельной задаче.
5. Принять конкретные технические пределы полей и объёма проекта (предложено 50 зон × 10 слоёв) или заменить их до реализации.
6. Выбрать дизайн-направление из 2–3 предложенных *после* утверждения GP.
7. **PROPOSED:** точная идентичность материалов обязательна: разные `material_spec_id` никогда не объединяются, одинаковые — только после явного выбора пользователем, при совместимых числовых параметрах. Принять этот вариант как продуктовую модель или предложить замену до начала реализации. Не создавать приложение без отдельной авторизации.

## 8. Запрет на расширение
Смена на многоугольники/карту/расчёт забора, теплицы, удобрений, плотности «по умолчанию» или монетизации требует нового scope. Любые формулы, UI, источники и PR — по `AGENTS.md`, `docs/development-contract.md`, `docs/cross-project-regressions.md`.
